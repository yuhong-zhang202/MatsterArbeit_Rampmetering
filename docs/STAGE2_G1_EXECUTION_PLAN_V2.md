## 1. 本次优化要解决什么

Robert 在原始邮件中支持先做无控制探索，特别关注主线 breakdown 附近的行为、实际需求注入，以及有限匝道储存与城市保护的冲突。原 G1 主要重复确认积压传播，未说明新运行如何推进主线/合流问题。

新版的唯一主要问题是：**在已保留的高需求无控制轨迹中，主线与匝道合流实际表现是什么；现有证据能区分哪些限制，下一步是否真的需要新仿真？**

执行后必须逐项回答：

1. 主线上下游各车道的流量、速度、占有率随时间怎样变化？全窗平均是否掩盖局部变化？
2. R 的计划出发、实际入网、经过匝道合流边界是哪些不同事件？证据是否支持匝道供给受限的描述？
3. 匝道积压、共享城市道路受阻及网外等待与主线状态在时间上如何对应？哪些因果解释仍不能成立？
4. 0/1500/1200 s 对这条轨迹支持什么观察、留下什么未决问题？是否有实际理由改变下一项检查的时长？
5. 最小下一步是什么：无需新运行、提出一个精确对照、提出一个具体测量缺口，或形成导师问题单？

H1「主线观测较通畅、匝道受限」、H2「主线存在局部拥堵现象」、H3「覆盖或辨别证据不足」只是解释框架。可以在不同位置/时段同时成立，不强制三选一，不是已批准的 breakdown 分类器。没有观察到预期现象不构成失败，也不允许强行调参产生它。

**推荐保留 A=0/1500/1200 s，但本轮仅重解释已有轨迹，不生成一条新轨迹。**

所有报告同时保留 demand end=1500 与 max end=2700 标记。1500 后的出流变化不能直接称 capacity drop。低速/停驶阈值 0.1 m/s 仅沿用旧技术描述，不能转为主线 breakdown 阈值。

三种时间语义不可混合：

1. 计划/入网/到达账目沿用 before-step：`scheduled < t`、`depart < t`、`arrival < t`。

### 9.3 R 合流通过事件的最小可行性检查

1. 不新开仿真。按 D1 确定的真实结构，先核对已知 R IDs 是否从匝道路径进入指定边界。
2. 本来源已确认没有 vehroute exit-times，仅用 vehroute 校验实际 R route/ID。不要寻找不存在的精确逐边时刻，更不能把上一个普通 edge 的 exit 猜作经过整个内部连接后的 entry。
3. 如果只用 FCD，则逐 R ID 记录前一有效车道/时刻与首次 `main_down` 样本时刻。需要路径来源可核验；记录事件在 `(t_previous,t_first_downstream]` 内，区间右端不是精确 crossing time。
4. 同一 ID 只计一次；下游换道不新增事件。首见即在下游、缺前样本、间隔不为原采样周期、路径不符、重复 ID/不单调、teleport 等分别记录，不 silently discard。
5. 若时间不确定区间跨 30 s 边界，不强行赋给一个精确区间。保留事件区间及边界不确定数；可另列“首次下游观测时刻计数”作为明确命名的采样代理，不冒充真实断面 30 s 流量。若报告每箱可能范围，不能把各箱上界相加作总量。
6. 对账全程唯一 R crossing IDs 与实际下游轨迹/已完成 R route 的覆盖；比较的是同一空间事件的覆盖，不把同时间 R 入网数当应相等。对未完成/未跨界/无法定位分别留状态。
7. 可行性通过后才将全量事件表作为证据；未通过则标 `not_measured` 或 `time_uncertain`，保留具体缺口。此分支的可接受交付是明确缺口，而非无限开发通用轨迹引擎。

本节测得的即使是准确通过量，也不是匝道可用容量、因果限流量或真实世界 capacity drop。

## 10. D4：三时段适配结论

负责人：data_analyst 提交证据，scientific_reviewer 审查解释。

1. 复用已有 A/B/历史切窗相关证据；仅补本轮主线时序需要的 A/B 摘要，不重复生成原 99 点 S1 报告。

6. 最终逐时段填：`retain_for_this_exploration` / `specific_change_proposed` / `insufficient_evidence`，并提供依据、用途、限制。状态是建议，不自动批准新时长。
