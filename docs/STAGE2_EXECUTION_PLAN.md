## 1. 阶段二究竟要完成什么

建议将阶段二限定为：**确认这个最小无控制场景测得清楚、需求是否实际实现得到解释，并形成一套可供下一阶段小规模需求探索使用的候选观察方案。**

阶段二要交付四个答案：

1. 车辆在哪里开始积压，怎样到达共享城市道路，记录覆盖是否足够？
2. 计划需求、实际入网、主线/匝道实际通过量、路内存量和网外等待之间是什么关系？
3. 预热、测量和清空应该怎样组织，哪些条件不能当作稳态处理？
4. 现有场景是否具备继续无控制需求探索的条件；如果没有，具体缺什么证据或修改批准？

本阶段**不要求必须出现** freeway Breakdown、Capacity Drop 或 sweet spot。没有观察到某种行为，是需要记录并解释的结果，不是自动调参直到出现该行为的理由。ALINEA、urban override、正式需求网格和论文结论均不包含在本方案的执行范围内。

本方案将“Ready for next exploratory step”与“Blocked with a specific question”区分；后者是明确交付的诊断结论，不冒充阶段二全部成功。

## 5. S1：先把现有证据收齐，不继续无边界地做动画

**顺序：simulation_engineer 技术检查 → data_analyst 汇总 → scientific_reviewer 审查。可独立的只读检查允许并行。**

目标是补齐一份全程诊断报告；不是制作一整套可视化平台。既有 390–430 s 片段直接复用。

工具前提：现有 replay 生成器硬编码 390–430 s 及事件断言，没有通用起止时间参数；旧 queue diagnostic 硬编码两个完整运行和四条普通边，不支持新运行、截尾或全内部路径诊断。不能直接向这些脚本传不存在的参数。优先使用已有结果；确需补片段时，S1 可包含经用户批准执行本步骤后所必需的最小离线参数化与边界测试，复用 `internal_lane_accounting.py` 的窗口功能。此类补丁不得调用 SUMO 或改变研究定义；它不同于 G1 后为新运行规则进行的 S3 实现。

### S1.1 事件和空间范围

将已有证据在同一时间轴排列：匝道末端停驶 → 储存段及内部连接积压 → 共享段 R/U 停驶 → 上游进口和网外等待 → 需求结束 → 最后入网 → 最后到达。

默认复用已有 46、192、412/414、656/661、1500、2245、2401 s 定位点，只在来源记录支持时引用。656/661 是持续网外等待片段开始，不是首次任意短暂入网延迟。上述时点只定位已有轨迹，绝不是推荐时长。

如已有文字/数值不足以解释某一具体疑问，最多补两段有明确目的的局部观察：

- 匝道末端：选择实际第一停驶事件附近的已有记录，检查让行、车道连续性和车辆移动，不凭动画判定主线 Breakdown。
- 上游积压：选择持续网外等待出现前后的已有记录；路内画面与网外等待计数分开，网外车辆不虚构坐标。

清空尾段优先用累计数和时间线，不默认再制作长动画。若必须补实况 GUI 检查，列明未检查的问题；只读离线回放不能替代它，也不能直接加载会写入原始输出目录的旧配置。需要新 SUMO 执行时将其纳入 G1 的具体授权。

### S1.2 统一观察面板

在同一轨迹上对齐以下已有量，必要新增分析仅写入新派生目录：

| 范围 | 必须区分的量 |
| --- | --- |
| M/R/U，X 单列技术交通 | 累计计划出发、实际入网、到达；未入网和仍在网分别记录 |
| 主线 E1 | 实际通过量、速度、占有率；保留上下游及车道范围 |
| 匝道进入合流区 | 先写明断面、车辆识别、数据来源和时间归属，再判断是否可计算；不能直接以上游 R 入网量代替 |
| 匝道到城市上游 | 外部/内部车道的车辆和停驶观察；不能用单一道路代替全路径 |
| 入网边界 | departure delay、网外等待数量随时间；不当作路内队列长度 |
| 需求结束以后 | 尚未入网、在网、到达和是否清空；不把“停止安排新需求”当成“停止入网” |

时间统计明确窗口端点、采样/聚合周期和单位。已完成车辆可利用实际入网与 departDelay 重建计划时刻；不把这种方法直接套到缺失或未完成车辆上。`departDelay` 与 `duration` 含义不同，见 [SUMO TripInfo 文档](https://sumo.dlr.de/docs/Simulation/Output/TripInfo.html)。

合流流量如果需要从轨迹过断面重建，先提出断面和事件计数规则、验证遗漏/重复及一秒采样的时间分辨率；不能把同窗口下游 E1 减上游 E1 自动解释为匝道合流流量，因为必须处理区间存量变化与通行时间。没有合格来源时记为未测得，并把测量补充放进确认包，而不是填入代理量。

### S1.3 诊断结果必须给出分支

- 仅看到入口排队：区分道路实际阻塞、信号约束和插入设置限制；没有反事实证据时保留原因 Unknown。
- 主线速度相似但网外积压持续增长：不能标为系统稳定；保留该条件为非稳态观察。
- 某问题必须改变几何/优先权/信号/行为参数才能区分：交付“一项具体假设＋一项最小区分检查”，转入 G1；本步不试着调参。
- 缺少可用测量：提出单一测量补充，不顺带改变交通行为。

**验收：**全程账目可解释，观察范围和缺口清楚，每个未决问题有下一项最小检查。最多完成一轮汇总和一轮针对审查意见的修订；仍不明的因果问题进入问题单，不继续无限拆分诊断。

建议产物：`data/processed/stage2_<run_id>/` 下派生数据与 manifest，`results/figures/` 和 `results/tables/` 下必要图表，`docs/STAGE2_DIAGNOSTIC_REPORT.md` 下结论及限制。所有新输出拒绝覆盖。

## 6. S2：形成观察定义、时段和运行候选的集中确认包

**负责人：主代理整合；data_analyst 提出可计算量；simulation_engineer 核对实现；scientific_reviewer 先审查。所有选择均为 Proposed。**

### S2.1 先确定观察问题，再选择秒数

候选必须回答：我们想观察从空网加载到排队的全过程，还是在某个可解释的初始化条件后比较固定期间表现？不能因为高需求不稳定就不断延长 warm-up，直至把排队开始删掉。

确认包只保留一个推荐方案和至多一个实质不同的备选。无证据支持全系统稳态时，明确报告“无法支持稳态解释”，可提出有限时域的全过程观察作为备选；这属于待批准的方法选择，不由执行模型擅自改写研究目标。

### S2.2 三个时段的候选依据

| 时段 | 候选依据 | 明确不能采用的理由 |
| --- | --- | --- |
| warm-up | 初始化/加载过程、主线和匝道状态、上游与网外积压、需保留的事件；同时展示从 t=0 开始的记录 | 只因某论文常用该秒数；只看主线平均速度；为了删除不利事件 |
| measurement | 要回答的问题、完整信号周期/聚合覆盖、计划与实际入网、状态随时间的变化；保持对比口径 | 不同条件随意改变窗口；挑选最平滑或最有利一段 |
| clearance | 停止安排需求后的待入网与在网车辆；提出最大仿真截止和未清空处理 | 只看路内车辆归零；把本次尾长直接当通用标准；无限延长直至通过 |

先用同一已有轨迹比较少量候选切点，清楚标为观察窗敏感性。若需试不同初始化/需求结束时刻，必须新列匹配条件的运行；不能把改变多个时段和总需求的历史运行当作单因素实验。

### S2.3 将质量判断分层

1. **执行有效性：**配置、状态、原始输出、警告及车辆账目是否可追溯。
2. **测量完整性：**时间和空间覆盖、内部车道、重复/遗漏、指标来源是否正确。
3. **需求期间解释资格：**请求量是否实际实现、网外是否持续积压；阈值未批准时使用 `not_evaluated`。
4. **车辆结果解释资格：**选中车辆群、入网延迟、尚未到达与截尾怎样处理。
5. **科学结论资格：**只能探索性描述；本方案不产生正式容量/因果/甜点区资格。

确认包必须给出每个拟采用标准的：字段、单位、空间范围、时间范围、计算方法、阈值及理由、失败后动作。无依据的阈值写 Unknown 并提出解决办法，不填“常用值”。总耗时如计算 `departDelay + duration`，标为从计划出发至到达的时间，不等同于因果额外延误，也不另加已经包含其中的路内等待。

### S2.4 代表性条件和运行预算

先按行为目标选择“低积压参考、可能过渡、明显受约束”至多三类无控制条件；不预设三种行为一定存在。已有需求点只作为有来源的探索锚点，不是冻结范围；不得根据 `qMain+qRamp` 简单相加就断言容量位置。请求需求、实际入网和进入合流区的流量分别记录。

**建议的工作量上限：初次批准包至多 6 个新探索运行。** 这是避免工作扩张的操作预算，不是统计学样本量结论。若采用三条件×两种子，精确条件、种子、时段及固定项必须在 G1 前列成六行运行表；它只提供早期敏感性线索，不能证明随机稳健性或支持正式统计推断。预算也可以更小，先执行信息价值最高的一项；不为凑满六项增加运行。

跨条件采用一致的候选观察规则和明确的固定项。涉及同一条件的技术修复前后对比时，用匹配种子及需求；不同种子不冒充匹配轨迹。已有结果只有配置、时段和统计口径确实一致才可复用为对应矩阵项，不为减少运行而强行匹配。

如现有证据不足以填写精确矩阵，G1 只申请一项定点诊断及其预算，不提交空白矩阵要求“全权执行”。

**S2/G1 交付清单：**推荐观察问题；三时段与最大截止的精确候选；测量/质量规则；允许的储存观察边界（不是自动批准有效储存）；精确运行矩阵；保持不变的项；代码缺口；运行数及失败重试预算；停止条件。用户只需对这一个具体包做集中确认。

## 7. S3：只补执行所必需的工具

## 8. S4：逐项执行批准的小规模无控制检查

**负责人：simulation_engineer。首次结果检查完成后才执行余项。**

每项保留 run ID、实际时间、软件版本、配置/代码快照或可验证指纹、精确需求和时段、seed、输出目录、日志、执行状态和分析状态。对 dirty worktree 不能仅用 Git commit 代表实际代码。

第一项完成后，先由 data_analyst 检查关键账目与覆盖。若发现工具层故障，暂停剩余项；若只是交通持续积压，这是观察结果，不把它当程序失败重跑。

全部任务有以下明确状态之一：未开始、运行中、执行失败、输出不完整、执行成功待分析、分析完成。失败任务不删除、不静默换 seed。新增运行不能超出批准矩阵；任何追加、替换、重试均受 G1 的明确预算约束。
