## Why the V6 method failed

V6 completed and was traffic-neutral, but its 30 `getLastStepOccupancy` readings disagree with XML in 173/238 lane-windows (independent data check), always below XML; mean difference −1.351785 percentage points and maximum −5.892472 percentage points. The V5/V6 interval API also disagrees. Therefore neither API value is accepted as the feedback measurement. These are measurement-path failures, not ALINEA outcomes.

In SUMO v1_26_0 `MSInductLoop.cpp`, `getOccupancy()` obtains completed vehicle records via `collectVehiclesOnDet(tbeg, false, false, true)`. Because `leaveTime=false`, a vehicle entering before `tbeg` and leaving within the step is omitted from that completed-record branch. `writeXMLOutput()` instead sums completed detection residence times, including `leftEarly` events, and ongoing detector residence to the interval end. `reset()` moves completed records to the last-interval container but retains ongoing vehicles. These source paths explain a systematic undercount mechanism, though the individual V6 vehicle discrepancies cannot be exactly reconstructed because V6 did not log per-vehicle E1 events. The same source defines `HAS_NOT_LEFT_DETECTOR=-1` and uses it for ongoing vehicle data. [SUMO v1_26_0 MSInductLoop.cpp](https://raw.githubusercontent.com/eclipse-sumo/sumo/v1_26_0/src/microsim/output/MSInductLoop.cpp), lines 46, 85–94, 227–239, 360–395, 428–459. The installed TraCI 1.26 Python client decodes `getVehicleData` as `(vehicle_id, length, entry_time, leave_time, type_id)`; SUMO's [official E1 TraCI reference](https://sumo.dlr.de/docs/TraCI/Induction_Loop_Value_Retrieval.html) documents the tuple fields.

## Prospectively fixed event accounting

- After each `simulationStep(t+1)` for t=600..4169, query `getVehicleData` for both existing `p1_main_down_20` lanes. This is read-only. Record every raw observation in `detector_vehicle_events.csv`. For an empty detector observation, write an explicit `event_count=0` sentinel, so both lanes have a checkable record for all 3570 seconds.
- Maintain one ledger across the complete controlled period, including XML 30 s reset boundaries. Key each event by `(detector_id, vehicle_id, entry_time_s)`. Repeated ongoing `leave_time_s=-1` observations remain one event; replace them when a finite exit time is reported. Identical repeated finite records are accepted once; changed metadata, conflicting exits, a missing active record, nonfinite times, or an absent/out-of-order second fail the run. Do not discard an ongoing vehicle at a 30 s boundary.
- At each decision t=630,660,...,4170, require exactly 30 consecutive seconds. For every ledger event, contribute `max(0, min(exit_or_t,t) − max(entry,t−30))` seconds. Sum **per vehicle**, including early departures and vehicles still on the loop; do not union overlapping event times or cap occupancy at 100%. Divide the summed seconds by 30 and multiply by 100 for each lane; mean the two lane percentages for the existing feedback law. An entry at t or exit at t−30 contributes zero. Completed events with exit≤t are pruned after accounting; ongoing events persist.
- Log `occupancy_source=vehicle_event_residence_30`, `sample_count=30`, both lane occupancy values and contributor counts in `feedback_updates.csv`. Keep `getLastIntervalOccupancy` and interval vehicle counts for diagnostic comparison only. V7 NOOP performs 119 observations with no `Feedback.update` and no signal write. An ALINEA card, if later released, would first apply the original feedback update at t=630. The 11% target, K=70 veh/h per percentage point, rate limits, pulse rule, first slot, geometry, input demand, seeds, 4200 s horizon, and other control gates do not change.
